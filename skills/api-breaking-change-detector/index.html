What the report contains

  • Verdict — counts of BREAKING / RISKY / DEPRECATION / SAFE — and a semver recommendation (MAJOR / MINOR / PATCH) with the reason.
  • Migration table your consumers can act on: severity, endpoint & exact spec location (JSON path), what changed, what consumers must do.
  • Which side breaks for each breaking change: request writers or response readers.
  • Changelog draft ready to paste, plus a “not breaking (so no one panics)” section.
  • Honest verdicts — a fully compatible diff is told it is compatible; no invented findings.

RISKY is a first-class category: new response enum values, changed defaults, new error codes — technically compatible, commonly catastrophic. A naive diff calls these safe.

What it does not do

  • It reviews the machine-readable contract only. It does not call your API and never fetches URLs referenced in the spec.
  • It cannot see runtime behavior that the spec does not describe (undocumented fields, server-side validation, rate limits).
  • Test against a staging environment before releasing — the report is a review, not a guarantee.

FAQ

Which formats are supported?

OpenAPI 3.x and Swagger 2.0, as JSON or YAML. Two full specs are needed; a partial diff or a screenshot is not enough.

How does it decide between BREAKING and RISKY?

BREAKING = an existing, spec-conforming client stops working (removed field, optional→required, changed auth). RISKY = the client still works today but is likely to break in practice (new enum value in a response, changed default, new error code).

Is my spec private?

The skill is a set of instructions for the agent you already use; nothing is sent to 43 Sunsets. What leaves your machine is governed by your agent’s own privacy settings.
